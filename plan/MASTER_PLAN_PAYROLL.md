## ١. السياق — لماذا هذا التغيير

المالك يستلم آخر كل شهر **ملف إكسل واحد** من محاسبي المشاريع، فيه لكل موظف:
الاسم · الصفة · تاريخ التعيين · أيام العمل · الراتب · سعر الصرف إن كان بالدولار ·
الخصومات · المكافآت · **الصافي المستحق** · وفي آخره **مجموع رواتب الموظفين**.
يدقّقه ويراجعه ثم يوافق على صرفه.

جزء من هذه الرواتب يُصرف من **سلفة تشغيلية** أُرسلت سابقاً إلى مشروع (البصرة مثلاً)،
فيصل ضمن ملف مصاريف السلفة سطرٌ اسمه «تسديد رواتب شهر ٢/٢٠٢٥». والمالك يريد
**ربط السطرين والتحقق من تطابق المبلغين** قبل أن يمسّ المال دفاتره.

**ما يعجز عنه النظام اليوم** (فُحص في الكود):

| الناقص | الموضع |
|---|---|
| لا صرف رواتب جماعي — موظف واحد في كل مرة | `SalaryNotifier.paySalary` |
| لا حقل «الصفة» ولا عملة للراتب — **الدينار حرفياً** | `employees_table.dart` · `paySalary` تكتب `currency: 'IQD'` |
| لا مفهوم «كشف شهر» يجمع الرواتب | لا جدول |
| لا ربط بين الرواتب وسلف المشاريع | `salary_payments` بلا `advance_id` |
| لا استيراد موظفين/رواتب من إكسل | الاستيراد الحالي للمصاريف فقط |

**النتيجة المرجوّة:** كشف رواتب شهري يُستورَد ويُراجَع ويُسدَّد — من خزينة مباشرة أو
من خلال سلفة مشروع بمطابقة محروسة — ويبقى لكل موظف سجل تفصيلي دائم بلقطة شهره.

## ٢. قرارات المالك الحاكمة (محسومة — 2026-08-24)

| # | القرار |
|---|---|
| ١ | **ملف رواتب واحد** شهرياً · **سند واحد بالمجموع** لكل دفعة صرف — لا سند لكل موظف |
| ٢ | **كشف شامل** للشهر · الاستيراد **تراكمي** · التسديد على **دفعات** حسب مصدر التمويل |
| ٣ | **لا يُحفَظ رقم بلا مقابل بالدينار** — أي مبلغ بالدولار يلزمه سعر صرف، وإلا يُرفض |
| ٤ | **٣٠ يوماً عرفاً** (قابل للتبديل إلى تقويمي من الإعدادات) |
| ٥ | الغياب · المكافأة · الخصم — **يدوياً** بآلية DMS (علَم يصون التعديل) |
| ٦ | **لا مكافأة نهاية خدمة ولا إجازات** — خارج النطاق نهائياً، لا مؤجَّلة |
| ٧ | خصم سلفة الموظف **اقتراحاً** يقرّره المالك |
| ٨ | **منع التعديل بعد التسديد** — التصحيح بالحذف وإعادة الإنشاء |
| ٩ | **التأكيد الذرّي** لا الإشعار اليدوي — الكشف يُعلَّم مسدَّداً داخل معاملة الاعتماد |
| ١٠ | الموظف الجديد **يُعرَض للموافقة** — لا إنشاء صامت |
| ١١ | **لا رقم موظف** — المطابقة بالاسم المُطبَّع + تاريخ التعيين، والغامض يُعرَض للبتّ |
| ١٢ | سطر رواتب بلا كشف → **تحذير يمكن تجاوزه** لا منع |

**الأصل المرجعي:** مشروع المالك المنفصل **DMS** — دُرس بالكامل (نظام رواتب ناضج).
⚠️ **يعيش خارج مستودع سند** (نُقل 2026-08-24: ٤ جيجا ومستودع git متداخل كان
يكسر قاعدة «المحلّل صفر»). تُؤخذ منه **الأفكار والحسابات والدروس**،
ولا يُنسَخ كوده: DMS نظام رواتب **بلا خزائن ولا سندات** (`PayAsync` لا تُخرج ديناراً
من أي خزينة)، والربط بالمال هو الجزء الذي نبنيه من الصفر.

## ٣. المخطط — Schema v7

### ٣٫١ جدول جديد واحد: `payroll_periods` (كشف شهر)

`lib/data/database/tables/payroll_periods_table.dart`

| العمود | النوع | ملاحظة |
|---|---|---|
| `id` | int PK | |
| `year` · `month` | int | `CHECK (month BETWEEN 1 AND 12)` |
| `fiscal_period_id` | int → `FiscalPeriods` | يُشتق من الشهر — يُفعّل `FiscalPeriodGuard` |
| `working_days` | int, default 30 | |
| `working_days_mode` | text, default `'fixed'` | `CHECK IN ('fixed','calendar')` |
| `exchange_rate` | real? | **مجمَّد على الشهر** — لا يتغيّر بتحرّك السعر لاحقاً |
| `status` | text, default `'draft'` | `CHECK IN ('draft','posted')` |
| `file_total` | real, default 0 | المجموع النهائي **كما ذكره الملف** — للمطابقة |
| `source_file_name` · `source_file_hash` | text | كشف الاستيراد المكرّر (نمط `advances`) |
| `notes` | text | |
| `created_by_user_id` · `created_at` · `posted_by_user_id` · `posted_at` | | أثر التدقيق |
| `is_deleted` · `deleted_at` | | حذف ناعم (القانون ٨) |

فهرس فريد `(year, month)` حيث `is_deleted = 0`.

### ٣٫٢ توسيع `salary_payments` — يصير **سطر الكشف**

> 🔑 **لماذا توسيع لا جدول جديد؟** جدولان يحملان معنى «راتب مدفوع» يعني أن تقرير
> «كم صُرف على الرواتب» يقرأ الاثنين — وهو **حرفياً** العطل الذي ضرب DMS: الجمع
> كان مكرَّراً في **ثمانية مواضع** فاحتُسب راتب صرفته شركة أخرى (٣٫٦٨ مليون).
> **مصدر حقيقة واحد.**

الأعمدة الجديدة (كلها بقيم افتراضية — إضافة بحتة):

| المجموعة | الأعمدة |
|---|---|
| **الربط** | `payroll_period_id?` · `advance_line_id?` · `advance_id?` · `treasury_id?` |
| **اللقطة** | `snapshot_name` · `snapshot_position` · `snapshot_currency` · `snapshot_hire_date?` |
| **الحساب** | `exchange_rate?` · **`net_amount_iqd`** · `eligible_days` · `eligible_days_is_manual` · `absence_days` · `absence_deduction` · `absence_deduction_is_manual` |
| **المقارنة** | `file_net_amount?` — الصافي **كما ذكره الملف** |
| **سلفة الموظف** | `advance_repayment_amount` · `cash_advance_id?` |
| **الحالة** | `payment_status` (`'unpaid'`\|`'paid'`) · `paid_at?` |

الموجود ويبقى: `employee_id` · `period_label` · `basic_salary` · `additions` ·
`deductions` · `net_amount` · `payment_date` · `voucher_id` · `notes` · `is_deleted`.

> ⚠️ `additions`/`deductions` تبقى «مكافأة» و«خصومات أخرى». خصم سلفة الموظف
> **عمود مستقل** — لولا الفصل لتعذّر تسجيل قسط السداد في `cash_advance_repayments`.

### ٣٫٣ توسيع `employees`
`position` (الصفة · text default `''`) · `salary_currency` (text default `'IQD'`, `CHECK IN ('IQD','USD')`)

`treasury_id` **موجود ويُستعمل كرابط المشروع** (قرار المالك) — موظفو خزنة البصرة
هم موظفو مشروع البصرة. لا حقل جديد.

### ٣٫٤ توسيع `advance_lines`
`payroll_period_id?` — السطر المُعلَّم «رواتب» يشير إلى كشفه.

### ٣٫٥ الترحيل v6 → v7 — `app_database.dart`

```dart
if (from < 7) {
  // payroll_periods أُنشئ أعلاه عبر createAll()
  await m.addColumn(employees, employees.position);
  ... (كل عمود جديد)

  // ترحيل بيانات حقيقي: السطور القديمة بلا لقطة ولا مقابل بالدينار

  //   net_amount_iqd ← net_amount  (كلها بالدينار اليوم — لا عملة قبل v7)
```

## ٤. طبقة الحساب — `PayrollCalculator` (نقيّة)

`lib/core/services/payroll_calculator.dart` — بلا قاعدة بيانات ولا واجهة، على نمط
`BalanceGuard` و`FiscalPeriodGuard` القائمين.

```
eligibleDays(year, month, workingDays, hireDate, terminationDate?)
suggestAbsenceDeduction(basic, absenceDays, workingDays)
netSalary(basic, eligibleDays, workingDays, bonus, deduction, absenceDed, advanceRepayment)
toIqd(net, currency, rate)            ← يرمي StateError إن كانت USD بلا سعر
ensurePayable(employeeName, net)      ← يرفض الصافي السالب عند التسديد
arabicMonth(month)
```

**قاعدتان منقولتان من DMS بأثر أعطال حقيقية:**

1. **الأيام تُسقَط لا تُعدّ.** الشهر أيام مرقّمة `1..workingDays`. العدّ كان يجعل
   شباط (٢٨ يوماً) حضوراً كاملاً قدره ٢٨ فيُصرف `28/30` من الراتب — أي ١٬٨٦٦$
   لمن راتبه ٢٬٠٠٠$ وقد داوم الشهر كلّه. (بلاغ مالك DMS 2026-08-05.)
2. **علَم «يدوي» لا استنتاج.** «قيمة موجودة» ≠ «قيمة اختارها إنسان». بدون العلَم
   كانت إعادة الحساب تمحو تعديل المحاسب، أو تتجمّد الأيام فيُحسب الصافي ببسط
   قديم ومقام جديد.

**اختلاف مقصود عن DMS:** هناك `ToIqd` تُعيد **صفراً** عند غياب سعر الصرف، لأن
الكشف يُولَّد من قاعدة البيانات **قبل** أن يُدخل المحاسب السعر — فالرمي كان يُنتج
قفلاً مغلقاً. **عندنا السعر يصل داخل الملف نفسه**، فلا قفل ولا مبرّر للتساهل:
`toIqd` **ترمي**، تنفيذاً لقرار المالك ٣.

### ٥٫١ مطابقة الاسم — بلا رقم موظف

```
تطبيع: إزالة التشكيل والتطويل · أ/إ/آ/ٱ→ا · ة→ه · ى→ي · توحيد المسافات
مفتاح المطابقة = (الاسم المُطبَّع, تاريخ التعيين)
```

| الحالة | التصرّف |
|---|---|
| تطابق تام | 🟢 يُربط بالموظف القائم |
| الاسم يطابق والتعيين مختلف | 🟠 **غامض** — يُعرض: نفس الشخص أم آخر؟ |
| موظفان بنفس المفتاح | 🟠 **غامض** — يُعرض للبتّ |
| لا تطابق | 🔵 **جديد** — يُعرض «سيُنشأ» وتوافق (قرار ١٠) |

**لا إنشاء صامت ولا ربط صامت أبداً.**

### ٥٫٢ ثلاث مطابقات تلقائية

1. صافي كل موظف: **المذكور في الملف ↔ المحسوب** — الفرق يُبرَز بالأحمر
2. مجموع السطور المحسوب ↔ **`file_total` المذكور في آخر الملف**
3. (لاحقاً عند الربط) مجموع الكشف ↔ مبلغ سطر السلفة

> نفس مبدأ `advance_lines.original_amount` القائم: **نحفظ ما قاله الملف ونحسب
> بأنفسنا ونُبرز الفرق** — فالغرض المعلَن من الملف هو «التدقيق والمراجعة».

### ٥٫٣ الاستيراد تراكمي
ملف البصرة يضيف موظفيه، وملف كربلاء يضيف موظفيه إلى **الكشف نفسه**،
و**لا يمسّ أيّهما سطراً قائماً ولا تعديلاً أدخله المالك بيده**.
(مبدأ `GenerateAsync` في DMS: *تراكميّ لا مُعيدَ بناء* — البديل يمحو ساعة عمل بضغطة.)

## ٦. التسديد — مساران

### ٦٫١ مباشر من خزينة
`PayrollRepository.payPayroll({periodId, entryIds, treasuryId, paymentDate})`

الحرّاس **بالترتيب** (كلها قبل أي كتابة):
1. الكشف `draft` — يمنع التسديد المزدوج
2. `FiscalPeriodGuard.ensureActive` — الفترة مفتوحة *(قائم)*
3. كل سطر بالدولار له سعر صرف — وإلا رفض *(قرار ٣)*
4. `ensurePayable` — لا صافي سالب
5. `BalanceGuard.checkSufficientBalance` — كفاية الرصيد *(قائم)*

ثم **معاملة ذرّية واحدة**: سند صرف واحد بالمجموع (`itemType: 'راتب'`، والبند
موجود في `_seedItemTypes` بترتيب ٩٠) ← تحديث السطور (`voucher_id`, `treasury_id`,
`paid_at`, `payment_status='paid'`) ← أقساط سداد سلف الموظفين ← إن سُدِّد الجميع
فالكشف `posted` ← سجل التدقيق.

### ٦٫٢ عبر سلفة مشروع — 🔑 قلب الطلب

**في شاشة مراجعة المسودة** (`advance_review_screen.dart`): علامة على سطر الرواتب
تفتح اختيار كشف الشهر، فيُملأ `advance_lines.payroll_period_id`، وتُعلَّم سطور
موظفي خزنة المشروع بـ`advance_line_id`. تُعرض المطابقة حيّة.

**في `AdvancesDao.postAdvance`** — الحارس في أعمق طبقة (القانون ٤):

```
لكل سطر له payroll_period_id:
   Σ(net_amount_iqd للسطور المرتبطة) == line.amount   (هامش ١ دينار للتقريب)
   وإلا → StateError عربي يسمّي الفرق ويمنع الاعتماد
```

السطر يصير **سنداً واحداً كالمعتاد** (لا تغيير في آلية `postAdvance`)، ثم — **في
المعاملة نفسها** — تُعلَّم سطور الكشف مسدَّدة بـ`advance_id` و`voucher_id`،
ويصير الكشف `posted` إن اكتمل. **لا نافذة نسيان** (قرار ٩).

**حوار الاعتماد يُظهر الأثر قبل وقوعه:**

```
🏷️ رواتب شباط ٢٠٢٥        ٥٬٠٠٠٬٠٠٠  →  سند واحد
✅ مطابقة: كشف شباط (موظفو البصرة) = ٥٬٠٠٠٬٠٠٠ — مطابق تماماً
⚠️ سيترتّب أيضاً: ١٠ موظفين يصيرون «مسدَّدين من سلفة رقم ٤٧» ويُقفَل تعديلهم
```

**سطر بندُه «راتب» بلا ربط** → تحذير قابل للتجاوز (قرار ١٢).

### ٦٫٣ خصم سلفة الموظف
الكشف **يقترح** قسط السلفة المستحقة من `cash_advances`، والمالك يقرّر (قرار ٧).
عند التسديد يُدرَج قسط في `cash_advance_repayments` بـ`method: 'salary_deduction'`
— **القيمة موجودة في الجدول منذ البداية وبصفر استعمال**، وتُوصَل الآن.
لا سند قبض: المال لم يتحرّك، بل خرج راتب أقل. `insertRepayment` القائمة تُحدّث
`total_repaid` والحالة ذرّياً.

**تحقّق المالك اليدوي (السيناريو الكامل):**
1. استيراد ملف رواتب شباط ٢٠٢٥ → مراجعة الفروق → حفظ مسودة
2. موظف جديد في الملف يظهر «سيُنشأ» ولا يُنشأ بلا موافقة
3. موظف براتب بالدولار بلا سعر صرف → **يُرفض برسالة تسمّيه**
4. استيراد سلفة البصرة → علامة على سطر «رواتب» → ربط بكشف شباط → **شريط المطابقة**
5. تغيير مبلغ السطر بدينار واحد → **يُمنع الاعتماد** ويُذكر الفرق
6. إعادته → الاعتماد يُظهر الأثر → بعده: **سند واحد** بالمجموع + الكشف مسدَّد
7. رصيد خزنة البصرة نقص بالمبلغ **مرة واحدة** لا مرتين
8. بطاقة الموظف تعرض تاريخه شهراً شهراً بلقطة كل شهر
9. محاولة تعديل كشف مسدَّد → **تُرفض**

## ١١. مخاطر معروفة وكيف تُعالَج

| الخطر | العلاج |
|---|---|
| **مضاعفة المال** — السطر يصير سنداً والرواتب تُحتسب ثانيةً | المطابقة المحروسة في `postAdvance`: المجموع لا يمكن أن يختلف. سابقة: ع-١٣ الرصيد الافتتاحي كان يُضاعف الرصيد |
| **مصدرا حقيقة لمجموع الرواتب** | جدول واحد + **دالة واحدة** تحسب الإجمالي، ويحرسها اختبار. سابقة: DMS جمعها في ٨ مواضع فاحتُسب راتب لم يُدفع |
| **الترقية تُفقد رواتب قديمة** | ترحيل `net_amount_iqd` صراحةً + اختبار `onUpgrade` على بيانات مزروعة (د-٩) |
| **مطابقة اسم خاطئة** | لا ربط صامت — الغامض يُعرض دائماً للبتّ |
| **شاشة الكشف تتضخّم** | تُقسَّم بـ`part` قبل ١٢٠٠ سطر · `tech_debt_guard_test` يُسقط البناء |
| **الأيام تُنقص راتب شباط** | الإسقاط لا العدّ + اختبار مخصّص لشباط |
